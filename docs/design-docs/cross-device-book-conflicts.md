# 多端重复扫码与书籍冲突方案

2026-10-29 用户已批准，现按此方案实施。原始候选先写入账户隔离的本机日志，再执行本机数据库事务。两步并非跨文件原子事务；启动同步时重放日志，且只有服务器确认本机别名 ID 不存在时才退休该别名。云端与本机均已有相同 ISBN 的不同 ID 时保留原记录，显示人工处理提示。发布前需单独验证服务端迁移和真实设备回读。

## 已确认的问题

2026-10-29 iPhone 16 的只读快照存在两条 `Right Ho, Jeeves`：规范 ISBN 都为 `9781841591049`，一条 ID 与 Mac 一致且已同步，另一条不同 ID、待上传。标题、作者、出版社、介绍链接一致，但标签/封面字段不同。现有拉取只按 ID 合并，服务端重复 ISBN 返回 409，客户端未逐项隔离冲突。不能直接丢弃其中一条，也不能把本地重复项的删除误发为对云端主记录的删除。

## 身份与规则

- 延续现有产品限制：同一认证账户的同一规范化 ISBN-13，在书库中只有一个活动记录。ISBN-10 先转成 ISBN-13；不同账户互不影响。
- 愿望单与书库是不同集合。仅两集合拥有相同 ISBN 不自动视为已购买；移入书库遇到已有 ISBN 时应提供“关联已有书籍并完成愿望”确认，不再创建第二本。
- 相同 ISBN 不是书名相似度推断。无 ISBN、ISBN 不同、仅书名相同的记录不自动合并。若未来需要同版多本实体副本，另行引入副本/数量模型，不复用重复 ID 绕过当前约束。

## 两台手机扫描同一本书

1. 扫码先检查本地规范 ISBN。已存在时提示“书库中已有此书”，提供打开已有记录，不新增 ID。
2. 两台均离线且都未见到该书时，允许各自保存临时记录与持久 outbox，这是离线使用的正常情况，不能要求录入必须联网。
3. 第一台联网后，服务器原子创建书籍，确定 canonical ID。第二台上传或拉取时发现相同 ISBN 不同 ID，返回/识别已有 canonical ID，不重复创建。
4. 客户端先把原始候选、canonical ID、读书状态快照写入持久日志，再在 SwiftData 事务中将本机临时 ID 退休并迁移阅读状态引用；异常中断后可以重放。退休操作不发服务器 DELETE。
5. 有矛盾字段时显示非阻塞“待处理冲突”；其余书籍、愿望、阅读状态继续同步。用户可随后选择“使用已有/使用本机/逐项合并”。确认前保留双方资料与可恢复快照，不用更新时间直接抹掉一方。

## 字段合并

| 内容 | 建议规则 |
|---|---|
| 书名、作者、出版社、介绍网址 | 相同则保留；一方为空可补齐；两方非空且不同则保留候选并由用户选择 |
| 标签 | 按既有规范化规则取并集；不丢失任一端标签 |
| 封面 | 保留可用封面及本机缓存；不同图片保留候选，不因 ID 归并删除文件 |
| 入库时间 | 默认保留较早有效入库时间；归并事务产生新的同步更新时间 |
| 阅读状态/完成日期 | 按阅读档案分别处理，不跨人覆盖；不同状态保留候选供确认，不简单采用“已读优先”，避免撤销已读的意图丢失 |
| 本机自有字段与关联引用 | 必须进入候选快照及迁移清单；不能因为旧服务端未支持该字段而丢弃 |
| 删除 | tombstone 与新增/编辑冲突需明确选择是否恢复；不自动复活已删除记录 |

## 技术实施边界

- 服务端必须使用原子唯一约束（owner + 规范 ISBN，活动记录范围）/事务抵御两台同时创建；现有“先 SELECT 再 INSERT”不能独立防止竞态。添加约束前只读审计旧重复数据并形成处置清单，不直接删除生产记录。
- 保留旧 Electron/PWA 的 409 行为；原生可使用兼容扩展的错误响应或专用解析接口获取同账户已有记录。响应不能泄漏别的账户记录。API/契约和安全测试随实施更新。
- 合并写入需要基于已读取版本进行条件更新并可重试，避免用户操作期间较新的修改被覆盖；ID 映射、候选快照和 outbox 在重启后继续有效。
- 单条 409 持久记录为待处理冲突并继续其他项；鉴权错误、网络中断与协议异常仍按其真实原因处理，不能一律当作冲突忽略。
- 覆盖正常在线重复、双离线扫码、同时上传、重启重放、ISBN-10/13、同名不同版、多档案、删除后重扫、愿望移入已有书、旧端兼容及跨账户隔离测试。
